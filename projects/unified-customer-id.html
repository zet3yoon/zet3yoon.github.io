롯데멤버스

마트 · 슈퍼 통합에 따른 단일 고객 식별 체계 구축

롯데마트와 롯데슈퍼가 한 회사로 합쳐지면서, 따로 운영되던 등급제와 포인트 제도를 하나로 묶어야 했습니다. 문제의 실질은 혜택 조정이 아니라 데이터 정의였습니다. L.POINT 연동 총괄로 매출 데이터 연계 기준과 반영 방식을 정의했습니다.

역할 L.POINT 연동 총괄
기간 2025.07 – 2026.01
협업 롯데마트 담당 조직 · 개발 · 운영
단일 고객 인식 마트·슈퍼·온라인 어디서 사도 같은 고객으로 인식
전체 구매 가치 한 고객의 온·오프라인 구매를 처음으로 합산해 산출
합병 대응 롯데마트·슈퍼 통합에 맞춰 등급 산정 구조를 하나로 통일

맡은 범위

기준 매출 데이터 연동 기준 · 등급 산정 항목 · 집계 단위 · 반영 시점
구조 업태별 매출 스키마 정규화 · 표준 속성 체계 정의
반영 등급 변동 시 L.POINT 반영 프로세스 · 운영 케이스 사전 검토
조율 롯데마트 담당 조직과 연동 기준 · 개발 적용 범위

문제 — 같은 고객이 매장마다 다른 등급

롯데마트·롯데슈퍼·온라인이 각각 등급제와 포인트 제도를 따로 운영했습니다. 고객 입장에서는 같은 롯데인데 마트에서는 상위 등급, 슈퍼에서는 하위 등급으로 인식됐습니다.

회사 입장에서도 문제였습니다. 오프라인과 온라인 매출이 각각 별도로 산정돼 한 고객의 전체 구매 가치를 통합적으로 볼 수 없었습니다. 누가 우량 고객인지 판단할 근거가 채널마다 흩어져 있었습니다.

합병으로 조직은 하나가 됐는데 데이터는 여전히 셋이었습니다.

결정 ① 혜택을 맞출 것인가, 데이터를 맞출 것인가

선택지
① 채널별 등급제를 유지하되 혜택 수준만 비슷하게 맞춘다
② 등급 기준을 통일하되 산정은 각 채널이 하던 대로 둔다
③ 매출 데이터 자체를 표준화해 하나의 산정 구조로 합친다
결정
③. 등급 산정에 어떤 매출을, 어떤 단위로, 어떤 시점에 반영할지부터 정의하고, 업태별로 다른 데이터 구조를 통합 산정에 맞춰 표준화했습니다.
근거
①은 고객이 겪는 불일치를 그대로 둡니다. ②는 더 나쁩니다. 기준은 같은데 산정이 다르면 왜 등급이 다른지 설명할 수 없는 상태가 됩니다. 같은 고객을 같게 보려면 세는 방식이 같아야 합니다.
함의
이 결정은 프로젝트의 성격을 바꿨습니다. 혜택 협의가 아니라 데이터 정의와 인터페이스 규격의 일이 됐습니다.

결정 ② 언제 반영할 것인가 — 운영 케이스를 먼저 봤습니다

데이터 구조를 맞춰도 시점이 어긋나면 고객은 오류로 인식합니다. 어제 산 것이 오늘 등급에 반영되지 않으면 고객센터로 전화가 옵니다. 반대로 매출이 취소됐는데 등급이 그대로면 회사가 손해를 봅니다.

그래서 시스템에 붙이기 전에 등급 변동 · 매출 데이터 갱신 · 등급 적용 시점에서 생길 수 있는 운영 케이스를 미리 검토했습니다. 각 경우에 무엇이 먼저 반영되고 무엇을 되돌리는지를 정해 두고 개발 적용 범위를 조율했습니다.

협업 — 요구사항을 모아 의사결정으로 넘기는 일

L.POINT 연동 담당으로 요구사항 정의 → 연동 정책 검토 → 개발 협의 → 이슈 커뮤니케이션까지 한 사람이 이어서 맡았습니다.

롯데마트 담당 조직, 개발, 운영이 각자 다른 것을 요구했습니다. 마트 쪽은 기존 고객 경험을 지키려 했고, 개발은 적용 범위를 좁히려 했고, 운영은 예외 상황을 줄이려 했습니다. 요구를 모아서 결정할 수 있는 형태로 만드는 것이 실질적인 일이었습니다.

성과와 배움

롯데마트·슈퍼 통합 등급제를 무사히 연동·오픈했습니다. 채널별로 나뉜 등급 산정 구조를 L.POINT 기반 단일 고객 인식 체계로 통합했고, 이후 통합 마케팅과 데이터 활용의 출발점이 됐습니다.

운영 케이스를 미리 검토해 둔 결과, 시스템 반영 이후의 안정적 운영 기반이 확보됐습니다.

통합의 실질은 데이터 정의입니다. 등급 통합이라고 하면 혜택 협의로 보이지만, 손에 잡히는 일은 어떤 매출을 어떤 단위로 어떤 시점에 셀지를 정하는 것이었습니다. 세는 방식이 다르면 결과는 반드시 다릅니다.

운영 케이스는 오픈 전에 봐야 합니다. 등급 변동과 매출 갱신이 겹치는 구간은 개발이 끝난 뒤에 발견하면 되돌리기 어렵습니다. 사전 검토가 오픈 이후의 안정성을 만들었습니다.

정책 · 데이터 · 조직이 동시에 엮이는 과제였습니다. 어느 하나만 정리해서는 끝나지 않았고, 여러 조직의 의사결정을 조율하는 경험이 됐습니다.
